# 執筆スタイルガイド（再構築版：ITインフラ・AI基盤 自習ガイド）

## 1. 読者と目標
- 読者：ITの予備知識がほぼない、知的な大人の初学者。「DBサーバー」が「データベースサーバー」の略だと知らない段階。「CPUの内部」と言われても機械のどこかを想像できない。ネットワーク図の箱・線・矢印の意味から説明が必要。
- 目標：発表者の口頭説明や外部検索なしで、**スライド本文と図だけ**で「何か」「なぜ必要か」「どこにあるか」「何がどう動くか」を理解できる。
- 子ども扱いしない。やさしく具体的な「です・ます」の日本語。
- 基本情報技術者試験の学習にもつなげるが、試験用語を知っている前提にしない。毎回「試験に出る」とは書かない。

## 2. 最重要の原則：前提を先に、遠くへ先送りしない
- 「このページまでしか読んでいない人が理解できるか」で判断する。
- 新しい用語は**初出のページで**、日本語の名称・必要なら読み方・略語の正式名称・やさしい意味を示す。英語を展開しただけ（例「DBMS＝Database Management System」）で終えない。各語（データベース／管理／システム）がこの場面で何を意味するかまで書く。
- 重要な用語は複数ページを使ってよい。次を具体的につなげる：
  1. 何を指す言葉か（機械・部品・ソフトウェア・データ・役割・通信の約束・サービス・考え方のどれか）
  2. 何のために必要で、ないと何に困るか
  3. 全体のどこにあり、何とつながるか
  4. 何を受け取り、何をして、何を返すか
  5. 身近な利用例と、混同しやすい用語との違い
- 説明に別の未説明語を使ったら、その語も補う（同じページか直前のページ）。
- 「処理」「資源」「実行環境」「基盤」「通信」「要求」「応答」「物理」「論理」「インターフェース」「規格」「プロトコル」など、普通の言葉に見えてITでの意味が分かりにくい語も、使う前に具体例で説明する。
- 文脈で意味が変わる略語（AP＝アクセスポイント／アプリケーションサーバー／アプリケーション、など）は、その都度何の略か明示する。この資料では「AP」単独表記は避け、「アクセスポイント（AP）」「アプリケーションサーバー」と書く。
- 久しぶりに出る用語や複雑な図のラベルには短い説明を添える：例「DBサーバー（データの検索・保存の依頼に応える側）」。
- 「詳しくは後ほど」「第○章で説明」だけで理解を止めない。仕組みの詳しい説明が要るなら直後の1〜3ページで扱う。遠いページへの参照は、基本を理解した人向けの発展・復習に限る。
- 用語集・索引は調べ直す補助。本文で必要な説明を用語集に追い出さない。
- 理解に必要な内容を発表者ノートだけに書かない（ノートは任意。書くなら補足のみ）。

## 3. 1ページの作り方
- 1枚につき中心の問い・テーマは1つ。必要なら同じテーマを「導入」「図で仕組みを見る」「具体例を追う」「似た言葉と比べる」「まとめ」の複数ページに分ける（すべてを同じ型にしなくてよい）。
- 見出しと単語の箇条書きだけで終えない。誰が何をして、なぜそうなるのか、原因と結果、前の説明とのつながりを文章で書く。
  - 悪い例：「メモリ：作業場所」
  - 良い例：「アプリを動かすとき、使うプログラムやデータを保存装置からメモリへ読み込みます。CPUはそれを使って処理を進めます。」
- 本文は22pt（キットの既定）。表は20pt、図のラベルは18pt（補足行16pt）。**文字を小さくして詰め込まず、ページを分ける。**
- 1ページの文章量の目安：本文だけなら全角で約230〜300字（22ptで12〜13行）。図があるページは図の見方と要点で80〜160字程度。収まらなければ隣に解説ページを足す。
- タイトルは1行（全角約26字以内）を目標。最大2行。
- lead（タイトル下の一文）は任意。使うなら1〜2行で、そのページの問いや前ページとのつながりを書く。
- 章の最初は `type:'chapter'` ページ（この章で学ぶこと／前の章とのつながり）。章の最後に「まとめ」ページと、確認の問い（`quiz`。問いページ＋解説ページが自動で2枚できる）を置く。大きな節の区切りにも短い問いを入れてよい。
- 各ページに `kind`（情報の区分ラベル）を付ける。元資料の区分を保つ：技術説明／一般的な構成例／説明用の例（説明用の仮定）／企業公表／公的統計／公開投稿の集計／原資料の提示条件／個別の体験談／原資料の想定／学習の提案／今回未確認、など（組み合わせ可：「技術説明・説明用の例」）。
- `src`：出典ID（S01〜S78、元資料と同じ番号）。技術の一般説明は S78（原資料B・Cの編集者による一般的な技術説明）を使う。この再構築で新たに足した基礎説明は 'S78' に加えて 'S79'（再構築時に追加した一般的な基礎説明）を付ける。
- `orig`：その内容が由来する元資料のページ番号の配列（例 [67, 68]）。新規に追加した基礎説明だけのページは `orig: []`。**元資料の全ページの内容が、どこかのページの orig に必ず現れるようにする（担当範囲で漏れなく）。**

## 4. 重点用語（濃い青）
- 基本情報技術者試験（IPA シラバス Ver.9.2 の範囲）に関係する用語は、本文・図・表で `{用語}` と書く。キットが濃い青（#0057A8）にし、**資料全体での初出だけ太字**にする。
- 用語の部分だけを `{}` で囲む。文全体を囲まない。色だけに頼らず、定義（名称と意味）が同じページの近くにあるようにする。
- 試験範囲外でも、資料の理解に必要な用語は同じくらい丁寧に説明する（青にはしない。必要なら **太字** で）。製品名（ProLiant、Tomcat など）・会社名・サービス名は青にしない。一般概念（クラウド、仮想化、DBMS、TCP/IP など）で試験に関係するものは青。
- 用語の定義は、`B.def({...})` カード、または slide の `terms: [{ t:'用語', alias:['略語'], read:'よみ', abbr:'略語', full:'正式名称', mean:'やさしい意味（索引に載る1文）', exam:true }]` で登録する（これが巻末索引の元になる）。def カードは自動で登録される。**`{}` で囲んだ用語は、必ずどこかで登録されていなければならない**（同じ表記か alias）。
- 登録は「その用語を初めて説明するページ」に1回だけ。別名（DB と データベース など）は alias にまとめる。
- 表記の統一：データベース（DB）、データベース管理システム（DBMS）、DBサーバー、アプリケーションサーバー（略して「アプリサーバー」も可。APとは書かない）、Webサーバー、ルーター、スイッチ、アクセスポイント（AP）、ONU、ISP、IPアドレス、MACアドレス、ポート番号、ストレージ、SSD、HDD、メモリ（主記憶）、CPU、GPU、OS、サーバー、クライアント、ブラウザー、インターネット、LAN、Wi-Fi、クラウド、仮想マシン（VM）、コンテナ。

## 5. 一貫して使う「説明用の例」（章をまたいで変えない）
- 買い物サイト「**サンプル商店**」（架空）。ドメイン名 `shop.example.com`（説明用に予約された名前）。
- 利用者：**佐藤さん**（顧客番号1、東京）。佐藤さんがスマホで「**注文履歴を見る**」を押す、が全編の一貫した例。
- 顧客表 customers：1 佐藤（東京）／2 鈴木（大阪）／3 高橋（福岡）
- 注文表 orders（order_id, customer_id, product, quantity, amount）：
  - 101, 1, ノート, 3, 3,000
  - 102, 3, ペン, 2, 1,200
  - 103, 1, ファイル, 5, 5,500
  - 追加の例（INSERT）：104, 2, 消しゴム, 4, 800
- 佐藤さんの注文履歴＝注文101と103（合計2行）。
- 家庭のネットワーク（元資料と同じ番号）：自宅LAN 192.168.1.0/24、PC 192.168.1.20、佐藤さんのスマホ 192.168.1.21、ルーター（LAN側）192.168.1.1、公開IP 203.0.113.50、サーバー 198.51.100.7、ポート443（HTTPS）、同じLANのプリンター 192.168.1.30、外のサーバー例 203.0.113.80。いずれも説明用に予約された番号。
- CPUの例：「100と200を足して、結果を残す」。
- 説明用に足したデータ・構成には必ず「説明用の例」と明記（kind か図の example:true か文中）。架空の統計・出典・企業情報は作らない。

## 6. 図の約束（全章で統一）
- 形（node の k）：
  - `machine`：機械（ハードウェア）。灰色・太い実線。アイコン例 FaServer FaDesktop FaMobileAlt FaHdd FaWifi FaNetworkWired
  - `part`：部品（CPU・メモリなど機械の中の部品）。薄い灰色・細い実線
  - `software`：ソフトウェア（プログラム）。紫。アイコン FaCogs
  - `data`：データ（書類の形）。緑
  - `db`：データベースを表す円柱の記号。緑。**初めて使うページで「円柱はデータベースを表す記号で、実物が円柱という意味ではない」と説明する（第5章）**
  - `role`：役割（点線）。`big:true` で役割の枠（中に機械やソフトを入れる）
  - `place`：場所・建物・範囲（破線の大きな枠）
  - `person`：人・利用者。`service`：外部のサービス・事業者の網など。`note`：注記。`label`：文字だけ。`chip`：小さな札
  - `hl:true`：今回説明する箇所を黄色の太枠で強調
- 線（edge の k）：
  - `cable`：機器の物理的な接続（ケーブル）。灰色の太線・矢印なし
  - `radio`：無線（電波）の接続。灰色の破線・矢印なし
  - `flow`：情報の移動（依頼・本文など）。黒の矢印。**必ず具体的な中身のラベル**（例「注文履歴を見せて」）と、順番があれば `n`（番号）
  - `ret`：返事（応答）の移動。緑の破線の矢印。ラベルと番号
  - `aux`：補助の問い合わせ（DNS・DHCPなど本文以外）。紫の破線の矢印
  - `power`：電力。茶色の極太線
  - 1つの図で使う線の種類は、図の見方（cap）で必ず説明する。
- 図の種類を使い分け、タイトルか cap で区別を書く：
  - 物理的な配置図（どこに何が置かれ、何でつながっているか）＝ place + machine + cable/radio
  - 機能・役割の関係図（何が何を頼むか）＝ software/role + flow
  - 時間順のやり取り図（シーケンス図）＝ `B.seq`
  - 層の図＝ `B.layers`
  - 比較＝表 `B.table` か `B.cards`
- 単純化した図には `simple:true`（「学習用に簡略化した図」の札が付く）。説明用データの図は `example:true`。
- 「実物の配置」と「理解のために並べた関係」を混同させない（cap に明記）。
- 図の近くに、その図の見方を短い文で書く（`cap`）。
- 図中の文字と矢印は大きく（ラベル18pt）。交差・重なりを減らす。ラベルの位置は `lx, ly` で調整できる。
- 継続した例では同じ基礎図を使い、今回説明する箇所を `hl:true` で強調する。
- 立体図や写真は使わない（このキットは平面）。機械の外観を示したいときは、外形の箱＋部品の配置図（上から見た図・断面のつもりの配置）と、学習用の模式図を組み合わせる。「上から見た配置の模式図」などと明記する。
- アニメーションは使わない。段階を追う説明は連続したスライドにする。

## 7. 正確性
- たとえ話と技術的な定義を区別する（`B.box('analogy', ...)` と `B.box('limit', ...)`＝たとえの限界）。
- 構成例を、すべてのシステムに共通する唯一の構成のように断定しない。
- 元資料の推定・仮定・個別の体験談・未確認事項を、確認済みの事実に変えない。区分ラベルを保つ。
- 元資料の重要な論点・比較・数値・条件・出典は保つ。重複は統合してよいが独自の情報を落とさない。
- 元資料に誤りがあれば直し、slide の `fix: '何をどう直したか'` に書く（変更一覧に集める）。
- クロック数と1秒あたりの命令数を同一視するなど、わかりやすさのために誤った説明へ置き換えない。
- 試験の範囲・制度について「確認済み」と書かない（IPAのシラバス本文はこの作業環境から閲覧できない）。

## 8. 参照
- 他のページへの参照は `[[p:ページID]]` と書く（ビルド時に「p.123」に置き換わる）。担当外の章のページは、OUTLINE.md の「アンカーID」だけ参照してよい。
- ページIDは `c05-03` のように「c＋章番号2桁＋連番」。chapter ページは `c05-00`。
